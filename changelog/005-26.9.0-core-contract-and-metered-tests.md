# Core-contract tests, metered licensing tests, and a local-build channel

## What changed

- Target bumped **26.8.0 → 26.9.0** (`Directory.Build.props`, `integration.yml` defaults,
  `examples/*.json`).
- **`MCP_SERVER_DLL` local channel.** `McpServerFixture` now launches a locally built server DLL
  when that variable is set, instead of `dnx <published package>`. The fixture exposes which
  channel it used, and failures name it.
- **`CoreContractTests`** — free, no licence needed. One test per shared defect the 2026-08-16
  audit confirmed on all 12 products: `fileName`-only input resolves; a missing file returns the
  promised `Available files:` listing; a missing required parameter is named; failures set
  `isError`; `get_license_status` is registered and reports a real engine version.
- **`MeteredLicensingTests`** (`Category=Metered`) — metered mode engages, output carries no
  evaluation markers, consumption is observable, and the keys never appear in tool output.
- **`metered.yml`** — a separate workflow, `workflow_dispatch` + weekly only.
- `integration.yml` now runs with `--filter "Category!=Metered"`.
- `ToolDiscoveryTests` asserts the **exact tool set** rather than a count of 3, and includes
  `get_license_status`.

## Why

The audit's validation round showed this suite could not have caught the defects it was supposed
to cover:

- Every call used `file:{filePath:...}`. The `fileName` form — the one the tool descriptions
  recommend, and the one that crashed all 12 products — appeared in no test anywhere.
- The unknown-file oracle was `IsError || contains("not found") || contains("available")`. The
  opaque `An error occurred invoking '<tool>'` sets `IsError`, so **the test passed on the exact
  defect being reported**. `CoreContractTests` asserts the promised text instead.
- Licence-dependent tests silently no-opped and were counted as Passed. So the metered tests do
  **not** skip when unconfigured — they fail, and the gating lives in the CI job where it is
  visible.

Separately, the suite could only ever run against a published package, so a release could not be
verified before it shipped. `MCP_SERVER_DLL` closes that gap: the same tests, the same protocol,
against the build on disk.

## Metered testing — read before enabling

**Every run of `metered.yml` spends real credit.** A metered key bills per operation, unlike a
licence file. Hence: dispatch/schedule only (never push or PR), weekly rather than nightly, one
OS rather than the 3-OS matrix, and a `concurrency` group so two runs cannot bill at once.

**Use a dedicated CI metered account with a capped balance, not the production key.** Then a leak
or a runaway loop is a red build instead of a surprise invoice.

Secrets required at repository or organization level:

| Secret | Notes |
|---|---|
| `GROUPDOCS_METERED_PUBLIC_KEY` | |
| `GROUPDOCS_METERED_PRIVATE_KEY` | Secret. Never echoed; no `set -x` in any step that can see it |

Secrets are not exposed to `pull_request` runs from forks, which is why the workflow has no PR
trigger.

The consumption-delta assertion **is enforced**. It was written observational, then verified
against a real key pair on 2026-09-01: the counter moves **immediately**, with no batching delay
to tolerate, so a flat counter means work was billed as nothing — worth failing on.

The assertion is `after > before` rather than a fixed amount, deliberately: observed deltas across
runs were 0.00180 and 0.00360 units for the same comparison on GroupDocs.Comparison 26.8, so the
per-operation charge is **not** a constant we should pin a test to.

Two other things that run confirmed, both previously open questions:

- **`GetConsumptionQuantity` returns without a connectivity error** and reflects usage instantly.
- **The quantity is account-wide, not process-local.** A freshly started server reported
  ~1.58e9 units; a process-local counter would start near zero. So treat `quantity` as a
  cumulative account total and `credit` as the meaningful remaining balance.

## Running locally

Against a local build, with no NuGet publish:

```bash
dotnet build ../GroupDocs.Comparison.Mcp/src/GroupDocs.Comparison.Mcp/GroupDocs.Comparison.Mcp.csproj

MCP_SERVER_DLL=<abs path>/GroupDocs.Comparison.Mcp.dll \
  dotnet test --filter "Category!=Metered"
```

Add the two metered variables and drop the filter to include the metered tests.

## Impact

`CoreContractTests` and the `get_license_status` case in `ToolDiscoveryTests` **will fail against
the published 26.8.0 package** until 26.9.0 is live — the repo's standing convention, since the
suite targets the published artifact. Use `MCP_SERVER_DLL` to verify before release.

## Verification

25/25 green against the local 26.9.0 build (`MCP_SERVER_DLL`). With no metered keys configured,
the 4 metered tests fail in 8 ms without launching a server — loudly, and at no cost.
