# A test that fails when a tool description names a tool that does not exist

## What changed

- Target bumped **26.9.0 → 26.9.1** (`Directory.Build.props`, the `integration.yml` input default
  and fallback, the `metered.yml` fallback, and `examples/*.json`).
- **`ToolDiscoveryTests.ToolDescriptions_OnlyReferenceToolsThatAreRegistered`.** Every backticked
  snake_case name in a tool description, and every backticked name the text calls a "tool", must be
  a registered tool. Result fields are camelCase (`changedText`, `fileName`), so they are not
  mistaken for tool references.

## Why

26.9.0's `analyze_changes` description told agents to *"use `compare_documents` instead"*. No such
tool is registered — the rendering tool is `compare` — so an agent following the advice got
"unknown tool" (audit finding M3, fixed in GroupDocs.Comparison.Mcp 26.9.1). The existing
discovery tests asserted the tool *set* and that descriptions were non-empty, so a description
pointing at a phantom tool passed. This test checks the rule rather than the one string.

## Verification

Proven in both directions before this entry was written:

| Server under test | Channel | Result |
|---|---|---|
| 26.9.0 (published) | `dnx`, test assembly built with `-p:McpPackageVersion=26.9.0` | **Fails**: `analyze_changes -> compare_documents` |
| 26.9.1 (local build) | `MCP_SERVER_DLL` | Passes; full suite 30/30, 0 skipped |

Note for anyone reproducing the red: the package version is baked into the test assembly at build
time, so `dotnet test --no-build -p:McpPackageVersion=…` does **not** switch versions — it launches
whatever the last build targeted. Rebuild with the property.

## Migration / impact

Integration runs need `package_version=26.9.1` once that release is published. Until then the
push-triggered run will fail to launch `dnx GroupDocs.Comparison.Mcp@26.9.1` — expected; dispatch
with an explicit `package_version` after the release.
